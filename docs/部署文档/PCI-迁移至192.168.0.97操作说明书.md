# PCI（iwork）迁移至 192.168.0.97 操作说明书

> 版本：v1.0
> 制定日期：2026-09-21
> 目标服务器：`192.168.0.97`（Windows Server，生产）
> 代码版本：`6aa2f8b`（含 PCI 文档前缀、今日目标分时分析、五状态完成判定、缅甸作息）
> 部署方式：离线包直跑（目标机不依赖 Git，不经过 GitHub Actions/GHCR 受控发布）
> 入口：沿用现有 Portal/Keycloak/Nginx

## 0. 前提与适用范围

### 0.1 前提假设

- **A1（同机拓扑）**：`192.168.0.97` 已运行 iwork 依赖的基础设施
  （MySQL `iwork_system`/`iwork_local`、Redis、Portal/Keycloak、Nginx、外部网络 `docker_dkt-net`），
  iwork 与基础设施**同机**部署，容器内可直接使用 `mysql`、`iwork-redis`、`DKT_kc_nginx` 等主机名。
- **A2**：`192.168.0.97` 可访问远程 payroll 库 `192.168.7.22:3306`（只读）。
- 若 A1 不成立（iwork 在另一台机器），按**附录 A** 补充网络、端口与反向代理改动。

### 0.2 适用范围

- 把当前 PCI 版本（离线包）部署到 `192.168.0.97` 的**新目录** `D:\DM\PCI-iwork`，接管既有 iwork 容器。
- 不迁移、不重建数据库与 Redis 数据；不修改 Portal/Keycloak/Nginx 配置（同机拓扑）。
- 本说明书属于已记录的偏差通道：绕过不可变镜像 Digest、生产预检、自动回滚、服务器准入与审计收据；
  风险与证据由使用方按组织流程登记（本机不自动改写 CI/CD 总方案）。

## 1. 迁移范围

## 4. 迁移步骤

### 4.1 本地生成离线包并记录摘要

```powershell
powershell -NoLogo -NoProfile -ExecutionPolicy Bypass -File scripts\New-IworkOfflineBundle.ps1 `
  -SourceRoot D:\iwork -OutputDirectory D:\iwork\dist
# 记录输出 JSON 中的 Bundle、FileCount 与 BundleSha256
```

### 4.2 传输、解压到新目录并校验

```powershell
# 传输 zip 到 192.168.0.97 后：
Expand-Archive .\PCI-iwork-offline-<时间戳>.zip -DestinationPath D:\DM\PCI-iwork -Force
Get-FileHash .\PCI-iwork-offline-<时间戳>.zip -Algorithm SHA256   # 与 4.1 的 BundleSha256 比对
# 抽查清单：清单路径为相对路径（正斜杠），可与解压目录逐项对照
Get-Content D:\DM\PCI-iwork\MANIFEST.sha256 | Select-Object -First 5
```

确认解压目录包含：`Dockerfile`、`docker-compose.yml`、`start.sh`、`entrypoint.sh`、
`requirements-prod.lock`、`deploy.ps1`、`env\production.env`、`iwork\`。

### 4.3 配置确认（同机拓扑无需修改）

- `env/production.env`：`ACCESS_DB_HOST=mysql`、`LOCAL_DB_HOST=mysql`、`REDIS_HOST=iwork-redis`、
  `IWORK_DB_HOST=192.168.7.22`、业务时区 `Asia/Yangon` —— **保持不变**。
- 密钥仅通过 `--env-file D:\DM\dkt-secrets.env` 注入（`deploy.ps1` 已内置该路径），不写入 profile。

### 4.4 记录并备份运行镜像（回滚保障）

```powershell
docker image inspect iwork-iwork:latest --format "{{.Id}}"
docker tag iwork-iwork:latest iwork-iwork:rollback-<时间戳>
```

说明：新目录构建会覆盖 `iwork-iwork:latest`；`up -d` 会重建容器，旧容器不再保留，
回滚必须依赖本次备份的镜像标签。

### 4.5 停旧实例（保证单写者）

```powershell
docker stop DKT_iwork DKT_iwork_alert_worker
docker ps -a --filter "name=DKT_iwork"             # 确认已停止；保留容器与卷用于回滚
```

> 同一台机器上只允许一套 iwork 在运行：两个 Celery beat 同时发布会互相覆盖快照版本。

### 4.6 部署启动

```powershell
cd D:\DM\PCI-iwork

# 仅当数据库为空库需要初始化时设置；已有数据时保持默认 false
$env:IWORK_RUN_MIGRATIONS='true'

.\deploy.ps1 -Environment production

# 关键补充：deploy.ps1 只启动 iwork，必须显式启动告警队列容器
docker compose --project-name iwork `
  --env-file .\env\production.env `
  --env-file D:\DM\dkt-secrets.env `
  up -d alert-worker
```

### 4.7 技术验收

```powershell
docker ps --filter "name=DKT_iwork" --format "{{.Names}} {{.Status}} {{.Image}}"
# 期望：DKT_iwork、DKT_iwork_alert_worker 均 healthy，镜像为 iwork-iwork:latest

docker exec DKT_iwork python manage.py check

docker exec DKT_iwork python -c "import urllib.request; r=urllib.request.urlopen(urllib.request.Request('http://127.0.0.1:8000/', headers={'Host':'iwork'})); assert r.status==200; print('internal HTTP 200')"

# 告警 Worker 健康
docker exec DKT_iwork_alert_worker celery -A iwork inspect ping -d "alerts@$env:COMPUTERNAME" --timeout 5

# 实时快照发布（等待 ≤ 60 秒出现 SUCCESS 行）
docker logs DKT_iwork --since 5m | Select-String "完整实时快照发布完成"

# 今日目标分时分析就绪（等待下一轮快照发布后检查）
docker exec DKT_iwork python -c "import json,urllib.request; h={'Remote-Subject':'verify','Remote-User':'verify','Remote-Groups':'/admin'}; r=urllib.request.urlopen(urllib.request.Request('http://127.0.0.1:8000/api/account/today-targets/',headers=h)); p=json.loads(r.read().decode()); print('status=',p['analysis']['status'],'groups=',len(p['groups']))"
# 期望：status= available；若为 unavailable，检查 payroll 连通与快照日志
```

### 4.8 入口与业务验收

1. 浏览器访问生产入口（如 `https://dituportal.dongming.local/iwork/`）：登录成功。
2. 实时数据页：数据正常刷新，SSE 有推送（浏览器网络面板可见事件流）。
3. 今日目标页：
   - 五状态卡片（已完成/逾期完成/未完成/已填写/待填写）与「今日实际/目标」正常；
   - 「今日目标分析」表可展开三段时段（07:30-11:30 / 12:00-16:00 / 16:30-18:30）；
   - 顶部「查看日期」选择历史日期后进入只读模式，历史分时分析可用。
4. 保存一组目标（目标 100、工时 10）后确认分析表中该组状态为「已填写」，且不因产量未达标而显示「未填写」。

## 5. 目录与项目名语义

- `deploy.ps1` 固定 `--project-name iwork`：无论从哪个目录执行，都会接管同一组容器
  （`DKT_iwork`、`DKT_iwork_alert_worker`），属于**接管式切换**，不是并行部署。
- 旧目录 `D:\DM\iwork` **原样保留、不再执行部署**；仅作为回滚与配置对照来源。
- 严禁执行 `docker compose down -v`；共享数据卷与数据库不得删除。

## 6. 回滚

```powershell
# 1) 停新实例
docker stop DKT_iwork DKT_iwork_alert_worker

# 2) 用备份镜像恢复
docker tag iwork-iwork:rollback-<时间戳> iwork-iwork:latest
docker compose --project-name iwork `
  --env-file D:\DM\PCI-iwork\env\production.env `
  --env-file D:\DM\dkt-secrets.env `
  up -d --no-build iwork alert-worker

# 3) 或直接从旧目录以旧配置重新拉起（旧目录未改动，等价于回到迁移前）
cd D:\DM\iwork
.\deploy.ps1 -Environment production -NoBuild
```

回滚后重复 4.7 的验收命令；同机拓扑无需回改 Nginx。

## 7. 风险与偏差登记

| 项 | 说明 | 处理 |
|----|------|------|
| 绕过受控发布 | 离线包不经 Digest、预检、自动回滚、准入与审计收据 | 由使用方按组织流程登记风险接受 |
| 准入收据不一致 | 该机装有生产准入与 `active-release.json`；手工替换后收据与实际容器不一致，下次受控部署会覆盖 | 记录本说明书的执行时间、版本与离线包 SHA-256 |
| 单机依赖 | iwork 与基础设施同机，97 维护即停机 | 安排在维护窗口，并保留回滚镜像 |
| 双写风险 | 旧实例未停就启动新实例会导致快照版本互相覆盖 | 严格执行 4.5 → 4.6 顺序 |
| 旧目录留存 | 旧目录被手工改动会破坏回滚 | 旧目录只读保留 |

## 附录 A. 跨主机拓扑差异（iwork 不在 97 本机时）

若 iwork 部署在另一台机器、只使用 97 的基础设施，需追加：

1. **配置**：新增 `env/remote-infra.env`，将 `ACCESS_DB_HOST`/`LOCAL_DB_HOST`/`REDIS_HOST` 指向 `192.168.0.97`；
   `IWOK_TRUSTED_PROXY_HOSTS` 使用 97 的 Nginx IP（IP 字面量，避免 DNS 依赖）。
2. **Compose 覆盖**：新增 override 文件，为 `iwork` 增加
   `ports: "<新机内网IP>:8000:8000"` 与 `extra_hosts: "DKT_kc_nginx:192.168.0.97"`
   （账号访问权校验 URL 在代码中硬编码为 `http://DKT_kc_nginx:8080/...`，必须借 `extra_hosts` 解析）。
3. **97 侧网络**：MySQL `3306`、Portal 管理接口 `8080` 已对内网开放；**Redis `6379` 未开放，需发布并仅放行新机 IP**。
4. **入口**：修改 DTD_nginx 的 `iwork.conf`，`proxy_pass` 由 `http://DKT_iwork:8000/` 改为 `http://<新机IP>:8000/`，
   执行 `docker exec DKT_kc_nginx nginx -t` 与 `nginx -s reload`。
5. **端口豁免**：8000 映射宿主机与“8000 只允许 docker_dkt-net 内暴露”的既有约束冲突，需正式登记偏差。
6. 其余步骤与第 2～8 节一致。

## 附录 B. 故障速查

| 现象 | 排查 |
|------|------|
| 容器持续等待 MySQL / Redis | `docker_dkt-net` 是否存在；`mysql`、`iwork-redis` 是否运行 |
| 经 Portal 返回 502 | 容器状态；`docker exec DKT_kc_nginx nginx -t` 后 reload；upstream 配置 |
| 分析长期 `unavailable` | payroll `192.168.7.22:3306` 连通性；`docker logs DKT_iwork` 中快照发布日志；Redis 连通 |
| 告警任务堆积 | `DKT_iwork_alert_worker` 是否启动；Redis broker 连通；`inspect ping` 是否 pong |
| SSE 无推送 | Nginx `proxy_buffering off`；Redis 通知频道；容器日志 |
| 迁移后页面是旧内容 | 确认新容器镜像与启动时间（`docker ps`），必要时重新 `up -d --build` |
