# iwork Redis 实时读模型与远程数据库隔离改造计划

> 日期：2026-07-31
> 状态：本地代码实施与隔离验证完成，待生产影子运行和生产验收
> 适用分支：`Keycloak`
> 目标系统：iwork 生产看板
> 本文档仅定义改造任务、验证方法和生产验收标准，不代表代码已经完成修改。

> 2026-07-31 本地实施记录：阶段 0～9 的代码、自动化测试和运行文档已经完成；
> 未连接服务器、未部署 Docker、未执行生产数据一致性对比和 50 用户生产验收。

## 一、背景与问题

iwork 当前使用以下数据层：

- 远程生产 MySQL：`192.168.4.19:3306/payroll`，Django 数据库别名为 `iwork`。
- 服务器本地 MySQL：Docker 容器 `DKT_mysql`，保存系统数据、本地历史快照、目标产量和生产订单等数据。
- 服务器 Redis：Docker 容器 `DKT_iwork_redis`，DB 0 用于业务缓存，DB 1/2 用于 Celery。

2026-07-31 的 50 用户生产只读压力测试发现：

- 50 条 SSE 连接和 SSE 数据本身正常。
- 1000 次页面/API 请求中出现 13 次 HTTP 500。
- 13 次错误全部来自远程 MySQL：`(1040, 'Too many connections')`。
- 远程 MySQL 的 `max_connections=151`，历史峰值达到 152。
- `workorders` 和 `processes` 是本次直接出现 500 的接口。
- SSE 每轮推送后，前端仍会再次请求 `workorders`，导致在线用户数直接放大远程数据库查询量。

静态调用链审计显示：

- 当前共有 23 个有效 API 路由。
- 其中 20 个 API 在某些情况下可能访问远程 MySQL。
- 12 个 API 在今日实时请求路径中直接查询远程 MySQL。
- 7 个 API 优先读取 Redis，但缓存未命中时会在 Web 请求中回源远程 MySQL。
- 1 个历史快照 API 会在 HTTP 请求内同步读取远程 MySQL。

现有 Celery 每 60 秒刷新 Redis 的基础结构已经存在，但部分 HTTP 接口没有消费现有缓存，且缓存未命中仍允许 Web 请求直接回源，导致 Redis 没有真正隔离客户端并发。

## 二、改造目标

改造后的数据链路必须为：

```text
192.168.4.19/payroll
        │
        │ 仅允许受控的 Celery 采集任务访问
        ▼
生产快照构建器
        │
        ├── Redis：今日实时读模型
        └── 本地 MySQL：历史快照
                 │
                 ▼
        HTTP API / SSE 只读服务器本地数据
```

硬性约束：

1. Uvicorn Web 进程禁止连接远程 MySQL。
2. SSE、页面接口、筛选接口只允许读取 Redis 或服务器本地 MySQL。
3. Celery 每 60 秒统一采集远程生产数据。
4. Redis 刷新失败时保留上一份完整快照。
5. Redis 未命中时禁止 Web 请求回源远程 MySQL。
6. 今日实时数据与历史快照必须按曼谷业务日期隔离。
7. 现有 URL、请求参数和响应字段尽量保持兼容。
8. 历史查询继续读取 `iwork_local`。
9. 不修改 Portal、Nginx、Keycloak 和公共认证配置。
10. 新旧 Redis 键增量并存，禁止上线时清空 Redis。

## 三、非目标

本次改造不包含：

- 修改远程生产 MySQL 的表结构、索引或权限。
- 单纯通过调大 `max_connections` 掩盖接口直连问题。
- 修改 Portal、oauth2-proxy、Keycloak 或 Nginx 公共配置。
- 修改生产订单每日 SQLite → MySQL 同步业务。
- 改变现有目标产量写入语义。
- 将历史查询重新切回远程数据库。

## 四、核心模块设计

### 4.1 深模块原则

不能让 20 个视图分别理解以下规则：

- Redis 键名。
- TTL。
- 当前快照版本。
- 陈旧判断。
- 上一版本回退。
- 缓存缺失错误。
- 分页和稳定排序。
- 原子发布过程。

这些复杂性应收敛到统一的实时读模型模块中。Web 视图和测试通过同一个模块接口访问数据。

建议模块结构：

```text
iwork/read_model/
├── __init__.py
├── store.py          # Redis 快照读取、发布和版本切换
├── builder.py        # 将远程查询结果组装成完整快照
├── schemas.py        # 快照结构、字段和业务不变量校验
├── queries.py        # Web 层使用的统一读取接口
└── errors.py         # 数据未就绪、快照过期等统一异常
```

建议外部接口：

```python
read_model.read(view_name, business_date, filters)
```

调用者不应知道 Redis 的具体实现。生产环境使用 Redis 适配器，测试环境使用内存适配器。

### 4.2 Redis 快照键

建议使用独立版本前缀，避免覆盖现有运行键：

```text
iwork:read:v1:{date}:current
iwork:read:v1:{date}:{version}:meta
iwork:read:v1:{date}:{version}:realtime:{stepno}
iwork:read:v1:{date}:{version}:processes
iwork:read:v1:{date}:{version}:workorders:{stepno}
iwork:read:v1:{date}:{version}:workorder-details
iwork:read:v1:{date}:{version}:detail:flows
iwork:read:v1:{date}:{version}:detail:flow:{flow}
iwork:read:v1:{date}:{version}:detail:stepnos
iwork:read:v1:{date}:{version}:detail:products
iwork:read:v1:{date}:{version}:kanban
```

### 4.3 快照元数据

每个完整快照必须记录：

```json
{
  "schema_version": 1,
  "snapshot_version": "20260731-142100-001",
  "business_date": "2026-07-31",
  "generated_at": "2026-07-31T14:21:00+07:00",
  "source_completed_at": "2026-07-31T14:20:58+07:00",
  "source_status": "success",
  "record_count": 12345
}
```

接口响应主体保持现有格式，通过响应头提供快照信息：

```text
X-Iwork-Snapshot-Version
X-Iwork-Generated-At
X-Iwork-Stale
```

### 4.4 原子发布

发布顺序：

1. Celery 查询远程 MySQL。
2. 在新版本键下写入全部数据。
3. 验证字段、记录数、汇总关系和业务日期。
4. 所有数据成功后，原子切换 `current` 指针。
5. 保留当前版本和上一版本。
6. 任一环节失败，不切换指针。

消费者只能通过 `current` 指针读取完整版本，禁止自行拼接不同版本的键。

### 4.5 陈旧数据策略

建议初始阈值：

| 数据年龄 | 行为 |
|---|---|
| 0～120 秒 | 正常提供 |
| 120～600 秒 | 提供上一份快照并标记 `stale=true`，前端显示更新延迟 |
| 超过 600 秒 | 实时接口返回 503“数据暂不可用” |

任何状态都不能由 Web 请求直接回源远程 MySQL。阈值必须放在配置中。

## 五、接口迁移范围

### 5.1 第一优先级：压力测试已失败的接口

- `GET /api/dashboard/processes/`
- `GET /api/dashboard/workorders/`
- `GET /api/dashboard/workorders/<wrk_order>/`

目标：

- 今日数据全部读取 Redis 快照。
- 历史日期继续读取本地历史快照。
- 工单完整列表和补充字段在 Celery 构建阶段生成。
- 工单排序固定为 `-total_qty, WrkOrder`。

### 5.2 SSE 和实时页面

- `GET /api/dashboard/stream/`
- `GET /api/dashboard/realtime/`
- 实时首页 `/iwork/`

目标：

- SSE 只读取完整快照。
- SSE 事件带快照版本和生成时间。
- 前端直接使用 `msg.data.workorders`。
- 删除每次 SSE 事件后的 `workorders` 重复请求。
- 工序列表从 Redis 读取。

### 5.3 其他实时统计与生产详情

- `GET /api/dashboard/hourly/`
- `GET /api/dashboard/flow/<flow>/`
- `GET /api/dashboard/monthly-trend/`
- `GET /api/dashboard/process-compare/`
- `GET /api/dashboard/heatmap/`
- `GET /api/dashboard/station-ranking/`
- `GET /api/dashboard/detail/stepno-overview/`
- `GET /api/dashboard/detail/flows/`
- `GET /api/dashboard/detail/flow/<flow>/`
- `GET /api/dashboard/detail/stepno/<stepno>/`
- `GET /api/dashboard/detail/product-overview/`

目标：

- 全部通过统一读模型读取 Redis。
- 删除 Web 请求中的远程回源。
- Flow、产品、工序和实时统计使用同一快照版本。
- 目标产量继续读取 Redis 或本地 MySQL。

### 5.4 产量看板

- `GET /api/kanban/stats/`
- `GET /api/kanban/ranking/`
- `GET /api/kanban/filter-options/`

产量看板支持 StepNo、WrkOrder、Flow 和员工组合筛选，不能为所有筛选组合永久生成单独缓存键。

建议流程：

1. 统计单日记录量和筛选维度基数。
2. Celery 构建最低必要粒度的聚合事实：`(StepNo, WrkOrder, Flow, RegPerSysID)`。
3. Redis 保存聚合事实和筛选索引。
4. 三个接口基于同一聚合事实筛选。
5. 排行榜使用稳定排序。

决策门槛：

- Redis 快照大小和 50 用户过滤性能达标：使用 Redis。
- Redis 过滤 P95 超过 500 毫秒或内存不可接受：使用服务器本地 MySQL 实时读模型，Redis 只保存热门结果和版本信息。
- 无论选择哪一种，本地 Web 请求都不得访问远程 MySQL。

### 5.5 历史快照接口

- `POST /api/history/snapshots/<date>/ensure/`

目标：

- HTTP 不再同步读取远程 MySQL。
- 快照不存在时提交 Celery 任务并返回 202。
- 前端使用现有 `retry_after` 机制轮询。
- 重复请求同一天只产生一个后台任务。
- 旧快照在新版本完成前保持可用。

- Celery 停止。
- Celery 任务执行超过 60 秒。
- 两个 Celery 任务同时启动。
- 部分 Redis 键写入后发生异常。
- 曼谷时间跨午夜。
- Redis 存在昨日残留键。
- 快照结构版本不兼容。

- 不发布半成品。

## 八、生产发布流程

生产优先推荐分两次发布。

### 发布 A：影子运行

- 新增读模型和新 Redis 键。
- Celery 同时生成新快照。
- Web 接口暂不切换。
- 连续观察至少 24 小时。
- 对比新旧数据、刷新耗时、远程连接和 Redis 内存。
- 不删除旧缓存键。

### 发布 B：接口切换

- 将全部实时接口切换到统一读模型。
- 启用 Web 远程数据库访问禁止规则。
- 重建 `DKT_iwork`。
- 执行接口冒烟测试。
- 先执行 5 用户试跑。
- 再执行 50 用户正式验收。
- 至少观察一个完整 Celery 刷新周期。

## 九、回滚方案

- 回滚到上一个 Docker 镜像或 Git 提交。
- 不清理 Redis。
- 不删除本地历史数据。
- 新 Redis 键使用独立 `v1` 命名，不覆盖旧键。
- 不修改共享 MySQL、Redis 数据卷。
- 回滚后立即验证 SSE、工单、生产详情和历史查询。
- 记录回滚原因和失败快照版本。

## 十一、完成定义

只有同时满足以下条件，才能认定改造完成：

1. 20 个远程相关 API 已完成迁移或明确采用本地实时读模型。
2. Web 进程无法访问远程数据库别名 `iwork`。
3. 50 用户生产测试零 5xx、零超时。
4. 远程 MySQL 连接数不随在线用户数增长。
5. SSE 同一轮所有用户获得同一快照版本。
6. 新旧业务结果通过完整一致性对比。
7. Redis、Celery 或远程数据库故障不会触发 Web 回源。
8. 生产发布、监控和回滚文档已经完成。
