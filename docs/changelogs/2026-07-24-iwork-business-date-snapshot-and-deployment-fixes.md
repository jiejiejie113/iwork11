# iwork 业务日期、历史快照并发与生产部署修复

- 日期：2026-07-24
- 分支：`Keycloak`
- 最终提交：`04def04536e2d025cd5449bb456b22b7534bfd5c`
- 部署目录：`D:\DM\iwork`

## 1. 修改目标

本次修改处理三类问题：

1. iwork 生产统计在北京时间、服务器时间和曼谷业务时间之间存在混用，可能在午夜附近读取或发布错误日期的数据。
2. 历史快照可以从 API、Celery 和管理命令等多个入口触发，原有入口级锁无法完整防止同一天的并发构建。
3. 生产部署暴露出 shell 脚本 CRLF 行尾、数据库密码配置不一致、健康检查 Host 错误以及健康检查重试提前终止等问题。

## 2. 生产代码修改

### 2.1 `iwork/settings.py`

修改内容：

- 新增 `IWORK_BUSINESS_TIME_ZONE`，默认使用 `Asia/Bangkok`。
- `CELERY_TIMEZONE` 与 iwork 业务时区保持一致。
- Django 全局 `TIME_ZONE` 继续保持 `UTC`，避免改变数据库时间字段的存储语义。
- 将班次开始时间、午休开始时间和午休结束时间移入 settings。
- 新增历史快照锁超时配置，默认 1800 秒。
- 新增历史快照锁续租间隔，默认 60 秒。
- 增加按业务日期隔离缓存键所需的配置。

修改理由：

- 生产统计的“今天”应按曼谷自然日计算，但不能因此改变 Django 和数据库原有的 UTC 存储策略。
- 班次参数集中配置后，统计代码不再散落硬编码。
- 历史快照可能长时间执行，需要通过可配置的超时和续租机制持续持有锁。

实际效果：

- API、Celery 和统计查询使用同一业务日期定义。
- 数据库存储行为保持不变。
- 锁参数可以通过环境变量调整。

### 2.2 `iwork/statistics.py`

修改内容：

- `_seconds_to_midnight()` 改为计算距离曼谷下一次午夜的秒数。
- 批量查询、详情查询和今日查询统一使用 `get_business_date()`。
- 相关查询支持显式传入 `target_date`。
- 班次和午休计算改为读取 settings。
- 新增 `detail_cache_key()`，详情缓存键包含业务日期。
- 新增 `realtime_process_list_cache_key()`，实时工序列表缓存键包含业务日期。
- 月度和详情缓存按业务日期隔离。
- 实时缓存命中时验证缓存数据日期。
- 远程查询开始前记录业务日期，查询完成后再次验证；如果查询期间跨过曼谷午夜，丢弃旧结果并重新查询。

修改理由：

- 服务器时区不一定等于曼谷时区，按服务器午夜设置 TTL 会在错误时间切换缓存。
- 不带日期的缓存键会让新业务日短暂读取前一天数据。
- 23:59 开始、00:00 后完成的远程查询可能将昨天结果写入今天缓存。

实际效果：

- 日缓存准确地在曼谷午夜失效。
- 不同业务日的缓存互不覆盖。
- 跨午夜的旧查询结果不会污染新业务日。

### 2.3 `iwork/api_views.py`

修改内容：

- 小时统计、Flow、月趋势、工序对比、热力图和工站排行的默认日期改为曼谷业务日期。
- 详情请求开始时只确定一次 `target_date`。
- 详情缓存的读取和写入都显式绑定该 `target_date`。
- SSE 工序列表和详情概览使用带日期命名空间的缓存键。
- 为缺少说明的函数补充中文 Google 风格 docstring。

修改理由：

- 同一次请求不能因为执行过程中跨午夜而在读取和写入阶段使用两个日期。
- SSE 连接持续时间较长，更需要日期隔离。

实际效果：

- 同一请求内日期保持稳定。
- API、SSE 和后台任务的日期口径一致。

### 2.4 `iwork/tasks.py`

修改内容：

- 每轮 Celery 实时数据构建只确定一个业务日期。
- 批量查询和详情查询显式使用同一个日期。
- 发布缓存前再次确认当前业务日期。
- 如果任务跨过曼谷午夜，放弃这一轮旧结果。
- 缓存写入显式携带日期。
- 历史快照发生锁冲突时正常跳过，不再当成任务失败。

修改理由：

- 一轮后台任务包含多个查询，不能让不同查询分别计算“今天”。
- 已有任务构建同一天快照是正常并发，不是系统故障。

实际效果：

- 一轮任务不会混合两个生产日期。
- 跨午夜旧任务不会写入新日缓存。
- 正常锁竞争不再制造虚假失败告警。

### 2.5 `iwork/history_store.py`

修改内容：

- 新增 `SnapshotBuildInProgressError`，表示同一天已有构建任务。
- 新增 `SnapshotBuildLeaseLostError`，表示任务执行期间失去锁所有权。
- 将快照锁从 API 层移入所有入口共同调用的服务层。
- 使用按日期区分的 Redis 锁，并使用唯一所有权令牌。
- 启动后台续租线程，每 60 秒续租一次。
- 在远程读取前、远程读取后、发布事务开始时、批量写入后和更新成功状态前验证锁所有权。
- 最终发布事务使用 `select_for_update()` 锁定 `HistoricalSyncState` 状态行。
- 快照版本号在数据库行锁内部计算。
- 失去锁的旧任务不能发布结果、标记 SUCCESS 或释放新任务的锁。
- 重建失败时保留上一份 SUCCESS 快照和事实数据。

修改理由：

- API 层锁无法阻止 API、Celery、管理命令以及多个 Worker 之间的交叉并发。
- 长任务可能超过初始锁有效期，必须自动续租。
- 仅验证锁是否存在不够，还要确认锁是否仍属于当前任务。
- Redis 锁之外仍需数据库行锁保护最终版本号和状态发布。
- 新快照失败不应破坏上一份仍然可用的数据。

实际效果：

- 无论从哪个入口触发，同一天同一时间只有一个有效构建任务。
- 旧任务失去锁后无法覆盖新任务结果。
- 快照版本不会重复或倒退。
- 重建失败时用户仍可读取上一份成功快照。

## 3. 容器与部署修改

### 3.1 `.gitattributes`

新增：

```gitattributes
*.sh text eol=lf
```

修改理由：

- Windows Git 可能将 shell 脚本检出为 CRLF。
- Linux 容器执行 CRLF 脚本时出现 `$'\r': command not found` 和 `set: -\r invalid option`，导致容器重启循环。

实际效果：

- 仓库中的 `.sh` 文件固定使用 LF，避免后续拉取代码时故障复发。

### 3.2 `start.sh`

修改内容：

- 将文件行尾规范化为 LF。
- 增加 Linux 容器要求 LF 的说明注释。
- 等待 MySQL、等待 Redis、迁移、静态文件、Celery 和 Uvicorn 等启动流程没有改变。

修改理由：

- 修复生产容器因 CRLF 无法执行启动脚本的问题。

实际效果：

- `DKT_iwork` 不再因 shell 解析错误持续重启。

### 3.3 `deploy.ps1`

修改内容：

- 容器内部健康检查请求增加 `Host: iwork`。
- 单次健康探测放入 `try/catch`。
- 单次失败记录退出码后继续轮询。
- 达到最大重试次数后才判定部署失败。

修改理由：

- 生产 `ALLOWED_HOSTS` 不接受 `127.0.0.1`，原检查会把正常服务误判为 HTTP 400。
- `$ErrorActionPreference = 'Stop'` 会让容器尚未就绪时的第一次连接失败直接终止部署，导致原重试循环无法工作。

实际效果：

- 健康检查使用生产允许的主机名。
- 应用启动期间的短暂连接拒绝不会中断部署。
- 持续无法启动时仍会在重试耗尽后报告失败。

## 8. 结论

本次不仅增强了恢复机制，也修复了已经发生的生产故障：

- 修复 CRLF 导致的容器启动脚本执行失败和重启循环。
- 修复 iwork 数据库密码配置不一致导致的连接与迁移失败。
- 修复错误 Host 导致的健康检查误判。
- 修复单次连接失败导致部署重试提前终止。

同时增加了预防性一致性保护：

- 所有 iwork 生产日期统一按曼谷时间计算。
- 缓存按业务日期隔离。
- 跨午夜旧任务不能污染新业务日。
- 多客户端和多入口并发构建快照时，同一天只有一个任务能够发布。
- 新快照构建失败时继续保留上一份可用快照。
