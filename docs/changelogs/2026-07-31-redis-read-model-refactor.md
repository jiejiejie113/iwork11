# 2026-07-31 Redis 实时读模型与远程数据库隔离改造

## 范围与状态

- 本次只修改本地仓库并执行隔离测试。
- 未连接 `192.168.0.97`，未拉取或修改服务器仓库。
- 未重建服务器 Docker，未修改 Portal、Nginx、Keycloak、oauth2-proxy 或共享数据卷。
- 生产影子运行、真实数据一致性对比和 50 用户生产验收仍待后续部署阶段执行。

## 问题原因

原 Web 请求在 Redis 未命中时可以直接查询远程生产 MySQL。SSE 每轮数据到达后，
浏览器还会额外请求一次工单接口。在线用户增加时，这两条路径会把用户并发放大为远程
数据库连接并发，最终出现 MySQL `1040 Too many connections` 和 HTTP 500。

## 修改内容与理由

### 1. 新增统一版本化读模型

新增 `iwork/read_model/`：

- `schemas.py`：校验必要视图、嵌套结构、业务日期和事实记录数；任一不一致都禁止发布。
- `builder.py`：由 Celery 在同一曼谷业务日期内构建实时、工序、工单、详情和 Kanban。
- `store.py`：先写完整版本键，回读校验后再单次切换 `current` 指针。
- `queries.py`：集中处理筛选、稳定排序、分页、Kanban 聚合和 SSE 同版本读取。
- `errors.py`：统一数据未就绪、结构不兼容和发布竞争异常。

这样做的原因是把 Redis 键、版本、陈旧判断、分页和失败策略封装在一个深模块中，避免
各个视图分别实现并产生不一致。

效果：

- 发布中途失败不会覆盖上一份可用快照。
- `current` 切换后即使清理更旧版本失败，新版本仍保持可读，不会被异常回滚路径删除。
- 当前版本和上一版本同时保留，旧版键按独立 `v1` 前缀增量存在。
- 0～120 秒正常提供；120～600 秒继续提供并标记陈旧；超过 600 秒返回 503。
- 不同曼谷业务日期使用不同 `current` 指针，不会跨日读取昨日数据。
- 响应头增加 `X-Iwork-Snapshot-Version`、`X-Iwork-Generated-At`、`X-Iwork-Stale`。

### 2. Celery 成为唯一实时远程采集入口

`sync_dashboard_stats` 现在执行：

1. 获取单日期采集锁，防止 60 秒任务重叠。
2. 构建一个完整快照，内部远程查询并发上限保持不超过 6。
3. 构建期间跨曼谷午夜时放弃旧日期结果。
4. 完整性校验通过后原子发布。
5. 每个线程池查询在自身线程的 `finally` 中关闭数据库连接，任务主线程也在结束时关闭
   `connections['iwork']`。

任务限制调整为软超时 55 秒、硬超时 60 秒。刷新失败时不切换 `current`，Web 继续读取
上一份完整快照。

### 3. 今日 Web API 全部改读本地快照

`api_views.py` 已删除对 `iwork.queries` 的导入。以下今日接口改读统一快照：

- 实时、工序、小时、Flow、月趋势、工序对比、热力图和工站排行。
- 工单分页和工单详情。
- 生产详情的 Flow、工序和产品视图。
- Kanban 统计、排行和级联筛选项。
- SSE 实时推送。

历史日期（包括工序对比、热力图和工站排行）继续读取 `iwork_local` 和已发布历史事实表。
实时快照不存在、Redis 不可用或
快照超过 600 秒时返回统一 503，不允许 Web 请求回源远程生产库。

### 4. 工单与 Kanban 共用最低粒度事实

Celery 新增一次 `(RegPerSysID, StepNo, WrkOrder, Flow)` 完整聚合查询，同时保存数量和源
记录数。采集层不提前删除隐藏或非白名单 Flow；工单按请求中的工序语义应用白名单，
Kanban 按 `show_all_flows` 应用隐藏规则。工单视图从事实构建员工去重、Flow、产品映射和
详情步骤；Kanban 三个接口从同一份事实筛选。

效果：

- 工单稳定排序固定为 `total_qty` 降序、`WrkOrder` 升序。
- 工单人数按员工 ID 去重，不会因跨工序重复计数。
- Kanban 统计总量与排行榜员工产量求和一致。
- 多筛选组合不需要永久创建大量 Redis 键。

### 5. SSE 移除重复工单请求

SSE 使用一次固定的 `current` 指针，同时读取实时、工序和详情视图。事件包含版本、生成
时间和陈旧标记。前端直接把 `msg.data.workorders` 写入第一页缓存，不再在每个 SSE 事件
后请求 `/api/dashboard/workorders/`。

效果：50 个在线用户每轮不再额外制造 50 次工单 API 请求，并保证同一事件的 KPI、图表
和工单来自同一快照版本。快照暂不可用时 SSE 发送 `snapshot_unavailable`，同时继续 15 秒
心跳，浏览器连接不会因单次刷新失败立即中断。

### 6. 历史快照确保接口异步化

`POST /api/history/snapshots/<date>/ensure/` 不再在 HTTP 请求中同步访问远程数据库。
缺失时只提交 `build_history_snapshot` Celery 任务并返回 202；同一天使用请求标记防止重复
入队。Redis 无法建立入队标记时返回 503，不会盲目重复提交；中间重试保留标记，耗尽
重试后释放标记，允许用户重新发起。实际数据发布仍由 `history_store.py` 的分布式锁和
本地 MySQL 事务保证。

### 7. 增加 Web 远程数据库硬保护

新增 `iwork/db_backends/guarded_mysql`。`web` 角色建立远程连接或创建游标时立即抛出
`RemoteDatabaseAccessDenied`。数据库路由器也拦截隐式远程读取。

进程角色：

- Uvicorn / runserver：`web`
- Celery worker / beat：`celery`
- migrate、导入和管理命令：`management`

`start.sh`、`start_dashboard.bat` 和 `manage.py` 已同步设置角色。即使未来视图误调用远程
模型，Web 进程仍不能真正连接生产数据库。

### 8. 配置、日志和文档

新增读模型键前缀、结构版本、保留时间、软/硬陈旧阈值、发布锁和刷新锁配置。Celery 日志
记录业务日期、快照版本、源记录数、刷新失败和锁状态。开发规范手册已更新为当前数据流。

## 本地验证结果

- Python：3.11.6。
- 全量测试：358 项通过；唯一警告是本机既有 `requests` 依赖版本提示，与本次逻辑无关。
- 新增覆盖：原子发布失败、当前/上一版本、发布竞争、日期隔离、结构版本、Redis 故障、
  陈旧阈值、Celery 防重叠、远程连接释放、历史异步入队、Web 数据库拦截、SSE 去重、
  工单稳定分页、Kanban 一致性。
- 50 用户本地并发测试：同时读取 SSE 载荷、工单和 Kanban，50/50 返回同一快照版本和
  一致总量。
- 静态边界测试：`api_views.py` 不允许导入 `iwork.queries`。
